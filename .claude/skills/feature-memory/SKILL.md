# 功能记忆与测试纪律

一句话:**先查历史再动手,做完先测再说完成,每个坑都留下记录,每个通过的测试都变成回归保障。**

不依赖临时记忆。任何有复用价值的经验都必须落到 `memory.md`。

---

## 0. 文件放哪(本仓库)

优先放在该功能代码所在的子项目里:

```
web/docs/memory/<feature>.md                        # web 侧功能
natively-cluely-ai-assistant/docs/memory/<feature>.md  # 桌面端功能
tools/<tool>/memory.md                              # 独立工具
```

跨子项目的功能放仓库根:

```
docs/memory/<feature>.md
```

规则:

- `<feature>` 用 kebab-case,和功能在代码里的叫法一致(`ai-interview-live`、`xhs-auto-post`)。
- **一个功能一个文件。** 不相干的功能不许共用一个 memory 文件。
- 目录不存在就建。

---

## 1. 动手之前:先查(不可跳过)

在分析代码、提方案、改任何一行之前,按这个顺序查完:

```bash
# 1) 当前功能自己的记忆
find . -path ./node_modules -prune -o -name "*.md" -path "*memory*" -print

# 2) 全部记忆里有没有类似的坑(换关键词多搜几次:报错原文、模块名、症状)
grep -rin "<关键词>" --include="*.md" . | grep -i memory

# 3) 历史测试用例
grep -rn "TC-\|REG-" --include="*.md" . | grep -i memory

# 4) 代码里的历史结论(本仓库的重要教训常写在注释里)
grep -rn "<关键词>" --include="*.ts" --include="*.tsx" <相关目录>
```

然后才是 git log / 项目文档 / 设计新方案。

**硬规则:不许在没查历史的情况下,重新尝试一个以前失败过的方案。** 如果 memory 里写了"方法 X 试过、失败、原因是 Y",就不要再试 X,除非能说明 Y 这个前提已经变了。

查完在回复里用一句话交代查到了什么(哪怕是"没有历史记录"),再往下走。

---

## 2. 动手过程中:边做边写

`memory.md` 不是收尾文档。以下任何一件事发生,当场回写:

- 定了一个技术选择 → 记选择 + **为什么**(以及否决了什么)
- 撞到报错 → 按第 3 节的格式记
- 试了一个办法没成 → **一样要记**,这是这份文档最值钱的部分
- 找到根因 → 记根因,不要只记现象
- 有了能跑的测试 → 按第 4 节记进去

判断标准:**如果三周后的自己(或另一个人)重新遇到这件事,这条记录能不能省下重新踩坑的时间?** 能就写。

## 3. 问题记录格式

```markdown
### ISSUE-00X:一句话说清问题

- 日期:
- 环境:            (OS / 版本 / 是否打包 / 哪个分支)
- 相关文件:        path:line
- 错误信息:        原文粘贴,不要转述
- 触发条件:        怎么才能复现
- 问题表现:        用户/调用方实际看到什么

**根本原因**

为什么会这样。写机制,不写"可能是"。定不下来就写"未确认,当前证据是 ___"。

**失败的尝试**

1. 方法一 —— 结果: / 为什么不行:
2. 方法二 —— 结果: / 为什么不行:

**最终解决方案**

改了什么,关键代码/命令/配置贴出来。

**验证方式**

怎么确认真的好了(命令 + 期望输出,不是"看起来正常了")。

**后续注意**

以后碰到什么信号要想起这一条。
```

关于"失败的尝试":**必须写,而且要写清失败原因。** 只记成功解法的文档,会让下一个人(包括未来的自己)把所有死路重走一遍。

## 4. 做完必须测,测完必须记

代码写完 ≠ 功能完成。至少覆盖:

- **核心成功路径**(必测)
- **主要失败路径**(必测:空值 / 异常输入 / 依赖不可用 / 权限不足)
- 按功能类型再挑:边界值、重复请求、并发、回归、接口联调、数据库落库状态、前后端打通

不要求机械跑满全部类型,但**成功路径和主要失败路径不能少**。

测试用例写进 memory:

```markdown
### TC-00X:用例名

- 测试目标:
- 前置条件:
- 输入数据:
- 操作步骤:
  1.
  2.
- 预期结果:
- 实际结果:
- 状态:PASS / FAIL
- 自动化位置:  path/to/test  (没有自动化就写"手动",并说明怎么手动跑)
- 最后验证:    YYYY-MM-DD
```

**只写"测试通过"不算数** —— 必须有输入、步骤和预期结果,否则下次没人能重跑。

### 改到「正在服务用户的东西」,必须当场验证它还活着

改一个**此刻正在被使用**的进程、代理、服务或配置(本机 dev server、隧道、常驻脚本、
launchd 任务)之后,**立刻用用户实际走的那条路径验证一次** —— 不是看进程在不在,
是真的发一个请求过去。

为什么单独列一条:这类故障**在本机毫无症状**。进程起来了、不崩、日志干净,只是不再
做该做的事;而用户那边是 502、是白屏、是「没反应」。两次真实案例:

- 给隧道代理加「被 import 时不自启」的判断,写成了拼字符串比较相对路径 → 判断恒 false
  → **代理永远不监听**。本机零报错,用户手机 502。
- 为了写测试重启 dev server → **配对码是每进程重新生成的** → 用户手机上的旧链接全部失效。

清单:
- 改完 → 用**用户的入口**验一次(公网 URL、手机链接、真实端口),不是 `pgrep`。
- 重启任何服务 → 检查有没有**每进程生成的东西**(配对码、临时凭据、端口),变了就主动
  告诉用户新的。
- 加「是不是入口文件」这类判断 → 用 `pathToFileURL(resolve(argv[1]))`,别手工拼 `file://`。

### 测试环境本身也要干净

跑测试之前确认没有会干扰的东西还挂着(后台脚本、上一次没关的进程、别的实例)。
**被自己的测试脚本污染出来的失败,和真 Bug 长得一模一样,而且更难看出来。** 结果可疑时,先怀疑环境,再怀疑代码。

---

## 5. 通过的测试永久保留

1. 以后再改这个功能,**必须重跑**它已有的用例。
2. 不许因为加了新测试就删掉旧的有效测试。
3. 测试逻辑确实要变 → 更新用例并写明**为什么变**。
4. 修完 Bug **必须**补一条能复现该 Bug 的回归测试,编号 `REG-00X`。
5. 所有历史通过的用例合起来就是这个功能的回归集。

回归测试的验收标准:

- 修复前跑 → **FAIL**(没验证过这一步的回归测试不算数,它可能根本没测到东西)
- 修复后跑 → **PASS**

## 7. 什么时候才能说"做完了"

以下**全部**满足才算完成:

- [ ] `memory.md` 已创建或已更新
- [ ] 动手前查过历史记录
- [ ] 代码完成
- [ ] 核心成功路径已测且通过
- [ ] 主要异常/边界已测
- [ ] 测试用例已写进 memory(带输入和预期结果)
- [ ] 该功能原有的用例已重跑通过
- [ ] 新踩的坑和解法已记录(**含失败尝试**)
- [ ] Bug 修复已补 `REG-` 回归测试,且修复前确实 FAIL 过
- [ ] 未解决的问题已明确写出

**只写完代码、没测、没更新 memory —— 不算完成,也不要向用户报告完成。**

如果某项确实做不到(比如环境跑不了自动化测试),**说出来**并写进"未解决问题",不要跳过后当作已完成。
